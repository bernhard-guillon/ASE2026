## Introduction
Modern AI deployments are commonly embedded in large software stacks. In
contrast, this project investigates how far a compact execution stack can be
pushed when neural operations are represented as first-class ISA extensions.
The objective is not to compete with full ML frameworks, but to design and
validate a minimal, inspectable path from trained model weights to executable
program behavior on a custom compute substrate.

This paper summarizes the implemented system in this repository: model export,
binary serialization, compiler and assembler integration, custom neural
instructions, RTL realization, and verification. The narrative is grounded in
measured and reproducible artifacts, including cycle-threshold benchmark JSON
files and automated parity tests.

## Scope and Exclusions
The implemented and evaluated workload is the neural character generation path
(input character code to framebuffer glyph output). Character-recognition work
was removed from the project and is intentionally out of scope for this paper
because it was not part of the final optimization and validation campaign.

## System Overview
The system is a co-designed stack with six layers:

1. Training/export artifacts (PyTorch model checkpoint).
2. Weight-export pipeline to JSON and compact binary.
3. Model compiler that emits RISC-V assembly and neural custom mnemonics.
4. Rust assembler (`rv32as`) plus GNU linker flow to ELF binaries.
5. Runtime backends: C++ emulator and Verilator RTL runner.
6. Test and benchmark harnesses for parity and cycle threshold evaluation.

The operational data path is:

`a0 character input -> one-hot mapping -> layered matvec + activation -> clamp/u8 -> framebuffer`

## Methodology: Iterative Co-Design
We used a strict iterative method:

1. Introduce one ISA/backend change (new mnemonic/opid/lane mode).
2. Extend compiler, assembler, C++ oracle mapping, RTL, and tests together.
3. Re-run targeted tests (encoding, execution, differential).
4. Re-run full regression gate.
5. Measure cycle-threshold impact and compare to previous phase.

This loop was repeated through x7b lane variants up to PMAC4. The key design
principle was behavior stability with isolated performance changes: semantic
output must remain identical while implementation throughput evolves.

## Toolchain from PyTorch to Executable Neural Binary
### Stage A: Export and Intermediate Representation
The weight-export pipeline (`projects/weight-export`) converts trained PyTorch
models into:

- Intermediate JSON (human-readable, debuggable).
- Compact binary format (`NRAL` header, layer table, packed float32 weights/biases).

The format and conversion logic are implemented in `model_formats.py`,
`export_generator.py`, and related loader notes. Weight transposition is
performed to match efficient row-major inference access patterns.

### Stage B: Model Compiler
`projects/emulator/model_compiler.py` loads exported JSON and emits assembly
with `.incbin` model blobs and execution code. The interactive compiler path
(`model_compiler_interactive.py`) drives framebuffer-oriented inference loops
and supports neural opcode/lane mode selection:

- `x77` custom opcode path.
- `x7b` enhanced path with lane modes:
  `base`, `4x`, `8x`, `8xpmac`, `8xpmac2`, `8xpmac3`, `8xpmac4`.

### Stage C: Assembly and Linking
The repository uses a custom Rust assembler (`projects/rv32_assembler`) with
GNU-compatible targets where possible, then links to ELF using GNU binutils.
The CMake flow builds neural ELF variants such as:

- `neural-op-enhance.elf`
- `neural-op-enhance4.elf`
- `neural-op-enhance8.elf`
- `neural-op-enhance8pmac*.elf`

## Custom Assembler and GNU Parity Strategy
`rv32as` provides deterministic encoding for RV32I, RV32F, and the project
neural custom instruction family. Parser/encoder support was extended for
mnemonics including `nmatvec8xp4.f32` (opid 9 on x7b).

Parity methodology:

- Byte-level `.text` comparison against GNU assembler output via `objcopy`.
- Scripted parity checks (`projects/rv32_assembler/test_parity.sh`).
- Integrated parity fixture/testing in emulator CMake (`parity/...` tests).
- Additional neural instruction blackbox encoding tests
  (`test_neural_instr_assembler.py`).

This ensured encoding correctness while enabling project-specific instructions
not available in stock GNU toolchains.

## Neural ISA Extension Rationale and Evolution
The ISA extension progression used CUSTOM0 (`0x77`) and CUSTOM3 (`0x7b`):

- Core ops: matvec, ReLU, sigmoid piecewise-linear, clamp-to-u8.
- Enhanced x7b variants introduced lane and PMAC scheduling alternatives.

The motivation was to reduce memory-access and accumulation overhead in the
matvec hotspot without changing model semantics.

Notable progression:

- `nmatvec8x` for wider lane handling.
- `nmatvec8xp`, `nmatvec8xp2`, `nmatvec8xp3` for PMAC scheduling attempts.
- `nmatvec8xp4` with true PMAC4 path (including fourth memory read port in RTL).

## Verification Methodology
Verification is multi-layered:

1. Unit tests for parser/encoder and runtime decode/execute.
2. Compiler/assembler blackbox tests for mnemonic emission and encoding.
3. Differential backend validation:
   `emulator_runner` vs `verilator_runner` output/return/framebuffer parity.
4. Full regression via CTest gate before accepting each phase.

Verilator differential validation is explicitly wired in CMake
(`python/verilator/differential_validation`) and neural enhance variants are
tested across configured lane modes.

## Optimization Results
Cycle threshold results are extracted from repository benchmark artifacts
(`documentation/collected-data/phase23/24/25-neural-lane-cycle-comparison.json`).

### Verilator backend (phase progression summary)

| Variant | Threshold cycles |
| --- | ---: |
| x7b-8lane | 400,000 |
| x7b-8lane-pmac | 200,000 |
| x7b-8lane-pmac2 | 200,000 |
| x7b-8lane-pmac3 | 200,000 |
| x7b-8lane-pmac4 | 150,000 |

Observed speedups at Phase 25:

- PMAC4 vs 8-lane: `400k / 150k = 2.67x`
- PMAC4 vs PMAC/PMAC2/PMAC3: `200k / 150k = 1.33x`

### C++ backend
For the evaluated thresholds in this setup, x7b lane/PMAC variants remained
flat at 1500-cycle threshold. This indicates the dominant gain in this phase
was captured in RTL scheduling/bandwidth behavior rather than in the C++ oracle
path.

## Discussion
Three engineering outcomes were most relevant:

1. Co-evolution of compiler/assembler/RTL was necessary; isolated changes were
   insufficient.
2. Differential validation prevented backend drift while enabling aggressive
   micro-architectural iteration.
3. PMAC3 plateaued, while PMAC4 introduced a measurable gain due to additional
   memory bandwidth and scheduling structure.

## Limitations and Threats to Validity
- Reported numbers are threshold-cycle based, not full wall-clock throughput.
- The workload is a compact FC pipeline; results may differ for larger models.
- Custom op semantics are project-specific and require toolchain coupling.
- Some parity paths (for broad assembler replacement) remain scaffolded for
  further hardening.

## Conclusion
This project demonstrates that a lightweight neural-execution stack can be
built and optimized through iterative ISA/runtime co-design while maintaining
strict correctness gates. The final PMAC4 x7b variant delivered meaningful RTL
speedup with preserved observable behavior. Equally important, the repository
now contains a reproducible methodology: export pipeline, custom assembler,
differential verification, and phase-based benchmarking.
